# 電話メモツール（phone-memo）

## 1. サービス概要

### このサービスはどんなサービスか

電話対応が本業ではない人のための電話メモツール。電話中は画面に並んだ質問項目を見ながら聞けるので、聞き漏れを防げる。選択肢をポチポチ押すだけで電話メモができあがり、チャットやメールにそのままコピペできる。

### 誰の、どんな課題を、どう解決するか

- **誰の**：電話対応に慣れていない、小さな会社の新人事務員。
- **どんな課題**：聞くべき質問項目が整理されていないまま電話を受けて、聞き漏れや折り返しが起き、ますます電話を苦痛に感じている。
- **どう解決するか**：質問項目が整理された画面で電話を受け、そのまま電話メモを作れるようにする。電話対応をルーチンワークとして、自信をもって取り組めるようになる。

## 2. このアイデアはどこから生まれたか

### 2-1. きっかけとなった体験・感情

19歳前後、メンテナンス会社の内勤でアルバイトをしていました。そこでは、電話応対が本業ではない事務員さんが、注文の電話や代表電話を受けていました。聞き忘れによる折り返しの電話や、「なんでこれ聞いてないの？」というやり取りは、新人さんに限らずあったと記憶しています。「最初から質問項目を整理して伝えてレクチャーしてほしい」というような場面を見ることもありました。

メモをして、必要に応じてメールをすることもあったようです。そういうルーチンワークのメールを作成するときに、ちまちまメールを作るのは手間がかかって大変そうだなと見ていました。

その後、コールセンターで13年働く中で、応対の結果をログに残すことも業務として行ってきました。ある程度のテンプレートはあるものの自由記述の部分が多く、ログ作成に時間がかかる場面が多々ありました。同じようなボリュームのある内容を毎回タイピングするのが、バカバカしく感じる場面もありました。

ふだんの応対では質問項目がだいたい決まっていて困らなかったのですが、イレギュラー案件のときに「これも追加で聞いてほしい」と言われ、終話後にお客様へ架電する場面では、内心で「先に聞くことを教えてくれ」とイラッとしたこともあります。

### 2-2. なぜそれが「気になった」のか

- **自分の性格**：無駄なことは効率化したい。ルーチンワークは仕組み化して、効率化したいと感じることが多い。
- **過去の経験**：コールセンターで働く中で、ログ作成時間を短縮するために自作のテンプレートを作り、実際にログ作成時間を短縮できたことがある。
- **大切にしている価値観**：工夫することは楽しい。

## 3. 課題の整理

### 3-1. 表に見えている困りごと

- 電話対応で質問項目をあらかじめ整理していないことで、聞き忘れ・聞き漏れが起きる。
- 電話対応はだいたい似たような話になることが多いのに、同じ内容を毎回手打ちでタイピングするのは時間がかかる。

### 3-2. 本当に解決したい課題は何か

**聞き漏れについて**

- なぜ？ 質問項目があらかじめ整理されていないことで、聞き忘れが起きる。
- なぜ？ 聞き忘れた内容を、折り返して聞き直す必要がある。
- なぜ？ 折り返すのが面倒だし、周りから白い目で見られるかもしれない。

**メモ作成について**

- なぜ？ 情報共有のために、電話の内容を手打ちするのは時間がかかる。
- なぜ？ 時間がかかることで、ほかの業務をする時間に影響が出る。
- なぜ？ 残業をしないといけない場面も出てくる。

→ **本当に解決したい課題**：電話対応に苦手意識を持つ人が、質問項目があらかじめ整理されていないせいで、ますます電話対応を苦痛に感じている。

## 4. 想定ユーザーについて

### 4-1. 想定しているユーザー

**ペルソナ**

- 従業員10人ほどの、地域の建材店（建材の卸・販売）で事務員として働く入社1年目（20代前半）。
- 事務作業の合間に、1日5〜15本ほど代表電話を取る。注文や見積もり依頼の電話も受けている。営業職への取り次ぎや、取引先から社長への電話にも対応する。
- 聞いた内容は、社内の営業職や社長に社内チャットで伝えている。

**年齢設定**

- 年齢：20代前半。
- 理由：LINEやInstagramなど、テキストでのやり取りが中心の世代で、電話対応に慣れていない人が多い。電話で聞くべき質問項目があらかじめ整理されていれば電話対応もしやすく、終話後の情報共有もツールですぐに作れるので、ルーチンワークを効率化できる。

**生活・状況設定**

- 生活・状況：従業員10人の地域の建材店（建材の卸・販売）の事務員（入社1年目）。ふだんの事務作業の合間に、注文や見積もり依頼の電話も受けている。現場や外回りで不在がちな営業や社長あての電話を受け、伝言を社内チャットで送っている。
- 理由：何を聞けばいいか考えながら電話対応をすると聞き忘れが起きやすく、終話後に情報共有の文章をいちいちタイピングすると時間がかかる。ツールを使えば、話しながら電話メモを作ったり、終話後にすぐ電話メモとして共有したりできる。

**環境設定**

- 環境：デスクワークでパソコンを開ける環境。社内チャットやメールで情報共有している。
- 理由：質問項目が表示されている画面を見ながら電話を受けることで、聞き漏れを防げる。ボタンを押すだけで文章ができるので、その都度タイピングする時間を節約できる。

### 4-2. 自分とユーザーの距離

**→ 身近な誰か**

19歳前後にメンテナンス会社の内勤アルバイトとして、事務員さんが電話対応をしているのを横で見ていた。ホームページ制作会社で法人営業をしていたときは、テレアポで事務員さんに電話をかける側だった。そして現在は、コールセンターのオペレーターとして13年以上電話を受けている。受ける側・かける側・受けるプロの3つの立場を経験しているので、電話対応における幅広いトラブルや困りごとが想像できる。

#### 大規模なコールセンター向けではない理由

- 守秘義務があるため現在の職場の具体的な状況は書けないが、コールセンターでは、AIが通話を自動で要約して応対履歴を作る仕組みが進んでいる（参考：[Amazon Connect の生成AIによる問い合わせ要約](https://dev.classmethod.jp/articles/amazon-connect-generative-ai-contact-summary-japanese/)）。
- コールセンターも、今後はAIが応対し、人間が対応する場面は少なくなっていくと考えている。
- そのため、大規模なコールセンター向けのログ短縮ツールではなく、電話対応が本業ではない人が電話対応するときのツールとして開発する。
- 小規模なコールセンターでも使えるツールへのアップデートや、別アプリとしての開発も将来的に検討している。

### 4-3. 実際に使われる可能性について（需要・存在確認）

- **まず最初に使ってくれそうな人は誰か**：仕事での電話対応がはじめての、建材店の新人事務員。
- **どんな場面でこのアプリを思い出すか**：電話対応で聞き忘れがあったり、情報共有のための文章作成に時間がかかって面倒だと感じたとき。
- **今、代わりに使っているもの**：メモとペン、パソコンのメモ帳、紙の電話伝言メモ。
- **それを置き換えてまで使う理由**：聞き忘れを防げる。情報共有の文章作成の手間が減る。紙の伝言メモの内容をチャットで送る場合は、結局タイピングし直す必要がある。

独学時代に作成した [log-shortener（React版）](https://github.com/miz0ken/log-shortener) を同僚に実際に触ってもらい、「マニュアルなしで直感的に操作できる」と評価をもらった。操作のしやすさは確認済みで、ターゲットである事務員さんの反応は、MVPリリース後に確かめる予定。

### 4-4. ユーザーがサービスを導入して利用するまでのイメージ（導入・継続の流れ）

- **知る・思い出すきっかけ**：電話対応で聞き忘れがあったり、情報共有の文章作成が面倒だと感じたとき。「電話伝言メモ テンプレート」「電話伝言メモ ツール」「電話伝言メモ Webサービス」などでGoogle検索して、このツールを見つける。タイトルタグに「電話伝言メモ」を入れる（SEOで上位表示されるかは不明。8章参照）。
- **最初の一歩**：会員登録は不要。よくある電話はサンプルとして用意してあるので、すぐに使える。パソコンのブラウザにブックマークしておけば、次からすぐ開ける。
- **利用を続ける理由**：ページを開いたまま電話を受ければ、質問項目を見ながら聞けるので聞き忘れを防げる。電話が終わったあとも、ボタンを押すだけで電話メモを簡単に作れる。聞くべきことをしっかり聞いて、抜け漏れのない電話メモを共有できることで、電話対応に自信がつく。

**toB向けとしての観点**

- **企業がこのサービスを導入する理由**：伝言を受け取る社長や営業にとって、メモの中身がそろっていて、抜けがなく、すぐ届く。メモを作る人のルーチンワークも楽になる。
- **機密情報や業務データを登録してもらうには**：作った電話メモは、コピーしてメールやチャットに貼る使い方。メモの文章はブラウザの中だけで組み立てるため、入力した内容はサーバーに送られず、保存もされない。サーバーにあるのは、質問項目と選択肢だけ。
- **乗り換えのハードル**：まずこのサービスを知ってもらう必要がある。また、作成したメモをサーバーに保存しないなど、セキュリティ上の懸念が少ないことを、すぐに分かってもらう必要がある。

| データ | 置き場所 | サーバーに送る？ |
| --- | --- | --- |
| 質問項目・選択肢 | サーバー（DB） | 送る（管理者が登録） |
| 電話で聞いた内容（メモの文章・相手の名前や連絡先） | 利用者のブラウザ内だけ | 送らない・保存しない |

## 5. 既存サービス・競合調査

### 5-1. 似たサービスの調査

**紙の電話伝言メモ（市販の伝言メモ用紙）**
- URL：https://www.amazon.co.jp/dp/B004BR7X8A
- どんなことができるか：電話の用件を簡潔にまとめられる付箋メモ。

**セコサポ「電話受付メモ」**
- URL：https://denkisekkei.com/denwa-uketsuke-memo/
- どんなことができるか：ボタンを押すだけで「誰から・誰に・用件」を記録し、電話しながら伝言メモが作れるWebツール。「登録不要」「データはブラウザ内だけ」「チャット用の文面をコピー」という特徴がある。

**ちょっとした電話メモ受け渡しチェック**
- URL：https://anysweb.co.jp/phone-message-check/
- どんなことができるか：電話を受けたあと、担当者へ渡す前に「誰から」「誰宛」「折り返しが必要か」「連絡先」「期限」「用件」の抜けを見直すための、小さなブラウザ内ツール。

**IVRy（アイブリー）**
- URL：https://ivry.jp/
- どんなことができるか：自動応答、電話転送、SMS送信、AIによる自動文字起こしなどで電話業務を自動化するSaaS。

### 5-2. それでも自分が作りたい理由

既存サービスの中で、自分が作ろうとしているものに一番似ているのはセコサポ。

- セコサポは、あくまでも**代表電話を取り次ぐ人**のためのもので、注文受付や見積もり依頼など、**自分で対応を完結させる人**向けのサービスではない。
- また、質問項目や選択肢を自分や自社でカスタマイズできないので、不便に感じる。
- IVRyは、AIが人の代わりに電話に出るサービスで、導入の手間もそれなりにかかると予想される。自分が作ろうとしているのは、ブラウザだけで完結し、導入の手間も最小限で、**電話に出る人を助ける**サービス。

### 5-3. 差別化を「体験価値」で表現する

**従業員10人の地域の建材店（建材の卸・販売）で働き始めたばかりの、電話が苦手で心臓がドキドキする事務員さんが、注文や見積もり依頼の電話を初めて一人で受ける瞬間を助けるアプリ。**

- 質問項目があらかじめ整理されているので、抜け漏れなく、聞くべきことを落ち着いて聞ける。
- 電話対応をはじめて行う人でも、スムーズに電話対応に入れる。
- 電話が終わったあとの電話メモ作成や情報共有の手間が減る。

### 6-1. ユーザーの変化

- **行動の変化**：質問項目をど忘れして折り返して確認することもあったが、整理された質問項目を見ながら電話対応できるので、聞き忘れが減る。終話後のメモや情報共有は、紙に書いたりキーボードでタイピングしたりしていたが、ボタンを押すだけで簡単に作れるようになる。

- **考え方の変化**：電話は「何を聞かれるか分からない、怖いもの」だったが、質問項目を見ながら何度も電話を受けるうちに、ルーチンワークだと考えられるようになる。

### 6-2. 価値を一文で表す

「このサービスは、電話対応に苦手意識を持つ人が、電話対応をルーチンワークとして、自信をもって取り組めるようになるサービス」

## 7. このアプリで実現すること

### MVPで作る機能

- **トップページ**：サービスの説明と、サンプルへの入口があるシンプルなLP。
- **サンプルの選択**：注文受付・見積もり依頼・代表電話の取り次ぎの3つ。サンプルは管理画面からいつでも追加できる。
- **聞き取り画面**：質問項目と選択肢を、ボタンで順番に選ぶ。電話中でも見やすいように、別ウィンドウで開ける。
- **電話メモの自動作成**：選んだ内容から、チャットやメールに貼れる文章をブラウザ内で組み立てる（入力内容はサーバーに送らない）。
- **電話メモの編集**：できあがった文章をその場で直せる。相手の名前や連絡先などはここで入力し、保存しない。
- **コピーボタン**：ワンクリックでクリップボードにコピー。
- **管理者のログイン・ログアウト**（管理者は自分のみ）。
- **管理画面**：カテゴリ・質問・選択肢の作成・表示・更新・削除。
- **デプロイ**

### 本リリースで作る機能

- 一般ユーザーの会員登録・ログイン・ログアウト。
- 会員が、自分（自社）専用の質問・選択肢を作成・編集・削除できる。

## 8. このアプリの懸念点とその対策

### 懸念点①：見つけてもらえない可能性

- **何が問題になりそうか**：SEOで上位表示されるか分からない。
- **なぜそう思うか**：現在のSEOの手法を把握していない。ツールのタイトルに検索されそうなキーワードを入れる予定だが、SEOにかけられる時間はそれくらいしかない。
- **そのために考えている対策**：XなどのSNSで紹介する。技術記事を書く。

### 懸念点②：チーム機能の工数

- **何が問題になりそうか**：本リリース以降に追加を検討している、部門で質問項目を共有する「チーム機能」は、招待の仕組みや役割ごとの権限チェックが必要になり、工数が大きく膨らむ。
- **なぜそう思うか**：今のスキルでは、設計をよく考えて作らないと、時間がかかりすぎたり完成しなかったりするおそれがある。
- **そのために考えている対策**：MVPは管理者1人に絞る。本リリースは「自分が作ったものだけ作成・閲覧・編集・削除できる」というルール1つにとどめ、チーム機能は将来の発展案として、設計を検証してから着手する。

## 9. 今後の展開・発展の方向性

- **ユーザーはなぜ使い続ける？**：苦手意識があった電話対応が、いつものルーチンワークになるから。
- **続けることで何が変わる？**：質問項目や選択肢を、自社に合うようにどんどんカスタマイズしていける。
- **データが溜まると何ができる？**：サーバーに保存するのは質問項目と選択肢だけで、メモの文章は保存しない方針。今後検討しているデータ集計機能をオンにした会社だけ、押された選択肢の回数や電話メモの編集時間を集計でき、その結果はその会社だけが見られる。
- **他の人と関わる余地はある？**：チームメンバーで質問項目や選択肢について話し合う会社もあると思う。
- **運用・仕組みで価値を出せないか？**：Googleアナリティクスを導入して、LPから実際にどれくらいの人が使い始めているか計測する。

### 今考えている発展案

- **機能追加の方向性**：チーム機能。管理者が質問項目と選択肢を作成し、その配下のメンバーが実際にツールを使う形にする。
- **UI・体験の改善**：ダークモードの実装。
- **機能以外の工夫**：業種ごとのサンプルを増やしていく。
- **AIとの組み合わせ**：判断に特化した高速なAI「Jev」（TypeSafe AI、早期アクセス中）を使い、聞き漏れのチェックや用件の振り分けができないか検討する。ただしメモの文章を外部に送ることになるため、利用者が明示的にオンにした場合だけ使う形にする（参考：https://typesafe.ai/blog/introducing-system-one-models-and-jev ）。

## 10. 技術スタック

### 10-1. 使用予定の技術

- **フレームワーク**：Ruby on Rails 8.1 ／ Ruby 3.4。
- **フロントエンド**：Hotwire（Turbo・Stimulus）、Tailwind CSS。
- **DB**：Neon（PostgreSQL）。
- **デプロイ先**：Render。
- **使用予定ライブラリ**：Rails 8標準の認証機能（管理者ログイン）。
- **その他**：Google Apps Scriptで10分おきに `/up` へアクセスし、スリープ対策。

### 10-2. 技術選定の比較検討

| 候補 | 採用/不採用 | 理由 |
| --- | --- | --- |
| Rails＋Hotwire | 採用 | カリキュラムで学んだRailsで、アプリ1つにまとめられる。管理画面のCRUDはRailsの得意分野。メモの組み立てはStimulusで足りる。 |
| React | 不採用 | 独学で作ったReact版はデータがハードコードだった。DBとつなぐには「Railsの中でReactを使う」か「Next.jsで作り直す」必要があり、どちらもカリキュラムで学んでいない技術の習得が必要になる。MVPの工数が増えるため、本リリース後に検討する。 |
| Laravel | 不採用 | 同じMVCの型だが、カリキュラムで学んでいないため、キャッチアップに時間がかかる。 |
| Rails 8標準の認証 | 採用 | ログインするのは管理者1人だけで、会員登録の画面は不要。コードが自分のアプリの中にあり、理解しながら直せる。 |
| Devise | 不採用 | 機能が豊富だが、MVPでは使わない機能が多い。 |
| Neon | 採用 | 無料プランに期限がない。保存するのは質問・選択肢だけで、容量が小さくて済む。 |
| Render Postgres（無料） | 不採用 | 作成から30日で期限切れになり、その後削除されるため、転職活動中に見せ続けられない。 |

### 10-3. キャッチアップ不足の懸念

- **完成までのハードルが高い**：Renderを使ったデプロイやNeonとのDB接続などは初めてなので、一定の時間がかかることが予想される。
